# Architecture

ProofRoute is organized around an Agent-View-Controller architecture because routing is only valuable when the decision path stays legible. The Controller receives raw prompt material and turns it into a ranked model decision. The Agent executes or simulates work around that decision, including OpenAI-compatible proxy lifecycle, provider forwarding, Ollama adaptation, benchmark orchestration, and asynchronous fanout planning. The View renders the proof in the terminal so a developer can understand the model choice, confidence, cost delta, and speed delta without opening a browser or learning a dashboard.

The Controller is intentionally local-first. The default classifier is deterministic and dependency-free, which makes the first run instantaneous, but the boundary is shaped for a GPU-backed classifier. An external backend can implement the same `classify(prompt)` contract by reading prompt JSON from stdin and returning an intent object with a name, confidence, ranked alternatives, and feature metadata, and the same command can accelerate multi-prompt paths by accepting `prompts` and returning either an intent array or a `data` array. That allows teams with multi-GPU workstations to attach an ONNX, TensorRT, vLLM, or custom embedding classifier through `PROOFROUTE_CLASSIFIER` or `classifier.command` without changing proxy semantics, benchmark rendering, provider execution, or fanout routing.

The Controller also exposes an asynchronous sidecar path for persistent accelerator services. When `PROOFROUTE_CLASSIFIER_URL` or `classifier.url` is configured, CLI and proxy routing call the local URL with a strict timeout and then normalize the returned intent through the same scoring path as the built-in classifier. This keeps GPU classification warm and amortized while preserving the near-zero decision budget through deterministic fallback. The `proofroute-classifier` binary is the reference implementation of that HTTP contract: it serves `GET /health`, `GET /metrics`, `POST /classify`, and `POST /classify/batch`, returns intent metadata without storing prompt text, and uses the built-in classifier so the sidecar can be tested on any machine before a team swaps in ONNX, TensorRT, vLLM, or another persistent multi-GPU runtime. Health, metrics, single classification, and batch classification responses carry backend name, declared lanes, visible device metadata, request count, error count, uptime, current inflight lane occupancy, per-lane request distribution, per-lane error distribution, peak inflight, and decision-time aggregates, while classification requests receive round-robin lane and device assignments. A sidecar instance can also wrap a stdin/stdout classifier command, and batch requests can be forwarded to a single `classifyMany` backend call before the sidecar enriches each result with lane and device evidence. The Controller can route batches while preserving the same prompt-fingerprint cache semantics as single routing, which lets demo, calibration, multi-agent planning, and fanout execution use a warm sidecar as a real accelerator instead of repeatedly crossing a cold per-prompt boundary. This gives production accelerator deployments a stable place to prove that the fast path is alive, balanced, and observable without leaking prompt content.

The Agent exposes that accelerator evidence through the same headless surface as the rest of the system. The `classifier` command derives the metrics endpoint from the configured classifier URL, applies the classifier timeout budget, normalizes the sidecar JSON, and returns either a structured warning for built-in or command-only modes or a renderable report for sidecar deployments. This keeps the Controller boundary observable without giving the metrics path permission to store prompt text or mutate routing configuration.

Routing uses hard context filtering before scoring. A model that cannot fit the estimated input and output window is removed before Softmax is applied, which prevents a visually confident but impossible route from reaching the Agent. The output side of that window can come from CLI `--output-tokens`, chat `max_tokens`, chat `max_completion_tokens`, Responses `max_output_tokens`, calibration samples, or the default estimate, which keeps context filtering and cost modeling tied to the request the developer is actually making. A request can also carry a maximum estimated cost or maximum estimated latency through metadata or the proxy headers `x-proofroute-max-cost-usd` and `x-proofroute-max-latency-ms`, allowing the Controller to reject over-budget or over-latency candidates before Softmax so hard operational ceilings cannot be overridden by quality preference. The policy can also arrive through `x-proofroute-policy`, which keeps transparent proxy control available to clients that cannot easily mutate JSON request bodies. Rejected models are still retained as structured evidence with the reason, required token budget, context window, executability, provider, locality, estimated cost, cost ceiling, estimated latency, and latency ceiling, so the trace can explain both why the winner won and why some models were never eligible. If every candidate is rejected, the Controller raises a structured no-route error with the same rejected evidence and the proxy returns an explicit 422 response instead of presenting a budget or context miss as an internal failure. The remaining models are scored with a blend of intent quality, context fit, local bias, requested-model bias, cost penalty, and latency penalty. Each candidate keeps those weighted components so a route can be rendered as an explainable trace rather than a black-box answer, and the probability distribution uses max-subtracted Softmax so very large positive or negative logits remain finite, which matters once real telemetry and dynamically learned weights enter the system. The Controller also keeps an in-process LRU route cache keyed by a short prompt hash plus token, output budget, cost ceiling, latency ceiling, policy, requested-model, and executability inputs; this avoids repeated classifier work without storing prompt text on disk, and proxy responses expose cache hits as routing evidence.

Dynamic policy weights sit above the scoring function rather than beside it. Balanced, save, fast, quality, and local policies all adjust the same quality, cost, latency, and local terms before Softmax is calculated. This keeps behavior tunable without introducing a second decision system, which is important for trust because every terminal explanation still comes from the same ranked candidate set.

The Agent is asynchronous by default. Proxy execution awaits exactly one selected provider path, while demo, proof, smoke, benchmark, calibration, and plan modes expose the router's value before any network call is made. Model discovery, readiness, CORS preflight handling, malformed JSON rejection, and proxy server lifecycle are also Agent responsibilities because they describe what the runtime can actually execute, not merely what appears in configuration. Local Ollama streaming is converted from newline-delimited JSON into OpenAI-style server-sent events, Anthropic streaming is converted from provider events into OpenAI chat completion chunks, OpenAI-compatible local and cloud streaming is passed through without buffering for chat completions, legacy Completions requests are adapted into the routed chat execution path and returned as text completion objects or chunks, and simple Responses API requests are adapted through the same route before being returned as Responses-shaped JSON or server-sent events. The runtime chooses protocol from provider kind rather than from the model's local flag, so a local OpenAI-compatible gateway can run without an API key while still benefiting from local routing bias, zero-price economics, and normal OpenAI-shaped request forwarding. When the selected provider returns a retryable 429 or 5xx failure, the Agent can retry the ranked fallback model and expose the switch through headers and telemetry, which keeps transient provider failure from turning an already-ranked route into a dead end. When a non-streaming upstream returns usage metadata, the Agent exposes actual token count, actual routed cost, and actual savings in response headers as well as the local ledger, giving SDK callers immediate evidence without asking them to parse a dashboard. The proxy also lists the router proof headers in CORS exposure, so browser-based editors and web sandboxes can read model, intent, decision latency, cache state, fallback state, token count, cost, and savings evidence after preflight instead of losing that proof behind default browser header filtering. The launch demo routes a fixed suite of representative prompts and aggregates savings, speedup, labeled intent accuracy, route mix, and p95 decision latency into a proof report, while the proof gate evaluates that report against explicit latency, savings, speed, request volume, and accuracy thresholds so the public performance claim can fail fast in CI instead of living only in README copy. The same proof gate can read the local telemetry ledger and evaluate real proxy traffic without prompt text, which connects the first-run proof to the day-two workflow where a team wants evidence from its own coding sessions. The smoke path starts a local fake OpenAI-compatible provider, routes a prompt, forwards an authenticated chat completion through the Agent runtime, and can also start the transparent proxy itself before calling `/v1/chat/completions`, which proves the SDK-facing entrypoint, CORS-exposed routing headers, upstream model swap, and response parsing without cloud credentials. The multi-agent planner produces a local fanout plan for architect, builder, reviewer, and optional specialist roles, while the fanout executor batches every executable-only route decision in one Controller pass and then dispatches the role prompts concurrently through configured providers before rendering status, latency, token usage, cost, savings, and output previews. These dry-run and execution modes are deliberately useful because they show whether an expensive model is being reserved for the part of the task that actually deserves it, then prove the distribution path can run when providers are configured.

Provider calls are bounded by an upstream timeout before the body is handed back to the proxy path. The global `router.upstreamTimeoutMs` value protects every provider by default, and an individual provider can override it with `timeoutMs` when a local daemon, remote gateway, or premium API has a different reliability envelope. A timeout is normalized into the same retryable failure channel as saturated or unavailable upstreams, so the Agent can execute the ranked fallback model instead of letting the transparent proxy stall inside a hung network hop.

The View treats the terminal as the product surface. It does not ask the user to trust a hidden score, and it does not bury the win in JSON unless JSON is requested. The default output is dense, colorful, and capture-friendly: the launch proof card, the shareable routing receipt, the CI-oriented proof gate, the drop-in proxy connection card with the browser-readable smoke proof command, shell-native proxy environment exports, the model catalog map, the classifier accelerator receipt, the proxy smoke receipt, selected model, detected intent, ranked alternatives, weighted trace terms, savings, speedup, controller p95 latency, calibration accuracy, prompt-suite economics, local routing ledger stats, telemetry-backed proof gates, and fanout economics are all visible in a single frame. The share view also has a Markdown mode that strips terminal control codes while preserving the same p95 latency, savings, speed lift, local-cloud split, intent mix, model mix, and copy line, which lets the proof move from a terminal screenshot into GitHub and launch posts without translation. This is the growth loop of the project, because the fastest way to explain a routing engine is to show representative prompts becoming cheaper and faster routes in under a millisecond, then give the developer a line they can paste into a launch post without translating the benchmark by hand.

Configuration stays plain JSON to keep the system auditable. Providers describe execution endpoints and credentials, while models describe context window, price, latency, throughput, and per-intent quality. The defaults are useful as a demonstration catalog, not as universal truth. Production users should replace the model economics with observed telemetry from their own prompts, then tune the router weights so the terminal proof reflects the workloads they actually ship. The `init` command can emit either the default catalog or a local OpenAI-compatible preset, which keeps the first configuration step inside the same headless workflow instead of sending a developer to copy a recipe by hand. For developers already running LM Studio, vLLM, or a private OpenAI-compatible gateway, `PROOFROUTE_LOCAL_OPENAI_BASE_URL` appends an executable local zero-price model to the merged catalog after JSON configuration is loaded, which preserves the default demo surface while turning a local gateway into a routable candidate with no config file.

The examples are intentionally executable rather than decorative. `examples/local-openai-router.json` demonstrates a local OpenAI-compatible gateway with no API key requirement, local pricing, local routing bias, and a command-backed classifier timeout, while `examples/classifier-command.js` proves the stdin/stdout classifier protocol for both `prompt` and `prompts`. That gives the repository a copy-pasteable bridge from the zero-dependency demo to real local model servers and eventual GPU-backed classifier processes.

Telemetry is local and deliberately narrow. The proxy writes a JSONL routing ledger that records model, provider, intent, estimates, status, and timing while omitting prompt text and completion text. When a non-streaming provider returns usage metadata, the ledger keeps actual input tokens, output tokens, total tokens, actual routed cost, actual baseline cost, and actual savings; when usage is unavailable, the same ledger preserves the route estimate so streaming and failure paths still contribute to the proof loop. This creates the proof loop needed for an open source routing engine: the user can run the proxy during real work, call `stats`, and immediately see whether the router is saving money and keeping decision latency low without exporting private development context. The same ledger can feed `share --ledger --markdown`, which turns a real coding session into a pasteable receipt while keeping the privacy boundary intact.

Tuning closes that proof loop without pretending to know more than the ledger can support. The tuner reads aggregated telemetry, estimates confidence from event volume, and recommends a policy plus router patch when the observed workload indicates stronger cost pressure, latency pressure, or local preference. It does not mutate configuration automatically, because the project should earn trust by explaining its recommendation before changing the routing surface. When the user explicitly asks for an export, the tuner writes a merged JSON configuration that can be reviewed, committed, shared, or discarded like any other local artifact.

Doctor diagnostics are part of the same headless experience. The command inspects the local Node runtime, configured model catalog, executable providers, lightweight upstream health, telemetry path, classifier mode, HTTP classifier sidecar health, and routing policy before the user points an editor, agent, or SDK at the proxy. Provider probes use local Ollama discovery or OpenAI-compatible model discovery when those endpoints are available, and an unreachable upstream is reported as a warning rather than a hidden surprise because the router can still classify locally and explain the missing execution surface. A configured classifier sidecar is probed through its derived `/health` endpoint so the terminal can show backend, lanes, and response time when the accelerator path is ready; an unavailable sidecar is also reported as a warning rather than a fatal error because deterministic local fallback preserves the routing path. This keeps the first run honest: a passing doctor output means the transparent proxy has at least one route it can execute against a reachable provider, a warning means routing is alive but execution deserves attention, and a failing output names the missing local or cloud prerequisite without requiring a browser dashboard.
