# Architecture

llm-router is organized around an Agent-View-Controller architecture because routing is only valuable when the decision path stays legible. The Controller receives raw prompt material and turns it into a ranked model decision. The Agent executes or simulates work around that decision, including OpenAI-compatible proxy forwarding, Ollama adaptation, benchmark orchestration, and asynchronous fanout planning. The View renders the proof in the terminal so a developer can understand the model choice, confidence, cost delta, and speed delta without opening a browser or learning a dashboard.

The Controller is intentionally local-first. The default classifier is deterministic and dependency-free, which makes the first run instantaneous, but the boundary is shaped for a GPU-backed classifier. An external backend can implement the same `classify(prompt)` contract by reading prompt JSON from stdin and returning an intent object with a name, confidence, ranked alternatives, and feature metadata. That allows teams with multi-GPU workstations to attach an ONNX, TensorRT, vLLM, or custom embedding classifier through `LLM_ROUTER_CLASSIFIER` or `classifier.command` without changing proxy semantics, benchmark rendering, or provider execution.

Routing uses hard context filtering before scoring. A model that cannot fit the estimated input and output window is removed before Softmax is applied, which prevents a visually confident but impossible route from reaching the Agent. The remaining models are scored with a blend of intent quality, context fit, local bias, requested-model bias, cost penalty, and latency penalty. The probability distribution uses max-subtracted Softmax so very large positive or negative logits remain finite, which matters once real telemetry and dynamically learned weights enter the system.

Dynamic policy weights sit above the scoring function rather than beside it. Balanced, save, fast, quality, and local policies all adjust the same quality, cost, latency, and local terms before Softmax is calculated. This keeps behavior tunable without introducing a second decision system, which is important for trust because every terminal explanation still comes from the same ranked candidate set.

The Agent is asynchronous by default. Proxy execution awaits exactly one selected provider path, while benchmark and plan modes expose the router's value before any network call is made. Model discovery and readiness are also Agent responsibilities because they describe what the runtime can actually execute, not merely what appears in configuration. The multi-agent planner currently produces a local fanout plan for architect, builder, reviewer, and optional specialist roles, then routes each role independently and reports the parallel critical path. This is deliberately useful as a dry run because it shows whether an expensive model is being reserved for the part of the task that actually deserves it.

The View treats the terminal as the product surface. It does not ask the user to trust a hidden score, and it does not bury the win in JSON unless JSON is requested. The default output is dense, colorful, and capture-friendly: selected model, detected intent, ranked alternatives, savings, speedup, controller p95 latency, calibration accuracy, prompt-suite economics, and fanout economics are all visible in a single frame. This is the growth loop of the project, because the fastest way to explain a routing engine is to show a real prompt becoming a cheaper and faster route in under a millisecond.

Configuration stays plain JSON to keep the system auditable. Providers describe execution endpoints and credentials, while models describe context window, price, latency, throughput, and per-intent quality. The defaults are useful as a demonstration catalog, not as universal truth. Production users should replace the model economics with observed telemetry from their own prompts, then tune the router weights so the terminal proof reflects the workloads they actually ship.
