# Architecture

ProofRoute is organized around an Agent-View-Controller architecture because routing is only valuable when the decision path stays legible. The Controller receives raw prompt material and turns it into a ranked model decision. The Agent executes or simulates work around that decision, including OpenAI-compatible proxy lifecycle, provider forwarding, Ollama adaptation, benchmark orchestration, and asynchronous fanout planning. The View renders the proof in the terminal so a developer can understand the model choice, confidence, cost delta, and speed delta without opening a browser or learning a dashboard.

The Controller is intentionally local-first. The default classifier is deterministic and dependency-free, which makes the first run instantaneous, but the boundary is shaped for a GPU-backed classifier. An external backend can implement the same `classify(prompt)` contract by reading prompt JSON from stdin and returning an intent object with a name, confidence, ranked alternatives, and feature metadata, and the same command can accelerate multi-prompt paths by accepting `prompts` and returning either an intent array or a `data` array. That allows teams with multi-GPU workstations to attach an ONNX, TensorRT, vLLM, or custom embedding classifier through `PROOFROUTE_CLASSIFIER` or `classifier.command` without changing proxy semantics, benchmark rendering, provider execution, or fanout routing.

The Controller also exposes an asynchronous sidecar path for persistent accelerator services. When `PROOFROUTE_CLASSIFIER_URL` or `classifier.url` is configured, CLI and proxy routing call the local URL with a strict timeout and then normalize the returned intent through the same scoring path as the built-in classifier. This keeps GPU classification warm and amortized while preserving the near-zero decision budget through deterministic fallback. The `proofroute-classifier` binary is the reference implementation of that HTTP contract: it serves `GET /health`, `GET /ready`, `GET /metrics`, `POST /warmup`, `POST /classify`, and `POST /classify/batch`, returns intent metadata without storing prompt text, and uses the built-in classifier so the sidecar can be tested on any machine before a team swaps in ONNX, TensorRT, vLLM, or another persistent multi-GPU runtime. Health, readiness, metrics, warmup, single classification, and batch classification responses carry backend name, scheduler, warmed state, warmup count, readiness requirement, batch window, max batch size, observed batch distribution, declared lanes, visible device metadata, optional device profile metadata, request count, error count, uptime, current inflight lane occupancy, per-lane request distribution, per-lane error distribution, peak inflight, and decision-time aggregates, while classification requests receive least-inflight lane assignment by default so new work goes to the coldest available lane under concurrent pressure; round-robin remains available as an explicit compatibility scheduler. Device profiles are normalized from a JSON profile map, from parallel CLI and environment fields for names, memory sizes, runtime labels, and driver labels, or from a bounded `nvidia-smi` startup probe when manual profile fields are absent. The probe is controlled by `PROOFROUTE_GPU_AUTO_DETECT` and `PROOFROUTE_GPU_DETECT_TIMEOUT_MS`, runs before the sidecar begins listening, and never enters the per-request routing path, which lets local accelerator proof show named hardware without charging every prompt a discovery tax. A sidecar instance can wrap either a spawn-per-call stdin/stdout classifier or a persistent NDJSON worker; the persistent worker protocol keeps model weights loaded, correlates requests by id, supports both `prompt` and `prompts`, and falls back deterministically when a response times out or becomes invalid. Explicit batch requests can be forwarded to a single `classifyMany` backend call, concurrent single-prompt requests can be microbatched through the same backend with a bounded batch window and max batch size, and warmup can drive a small prompt-free classifier suite through the same path before real proxy traffic arrives. Startup warmup through `--warmup` or `PROOFROUTE_CLASSIFIER_WARMUP` reuses that same HTTP route after listen, while `--require-warmup` or `PROOFROUTE_CLASSIFIER_REQUIRE_WARMUP` keeps `GET /ready` at 503 until warmup has passed, so a deployment log and health endpoint can both prove the worker is warmed before an editor or SDK sends its first proxied request. The Controller can route batches while preserving the same prompt-fingerprint cache semantics as single routing, which lets demo, calibration, multi-agent planning, and fanout execution use a warm sidecar as a real accelerator instead of repeatedly crossing a cold per-prompt boundary. This gives production accelerator deployments a stable place to prove that the fast path is alive, warmed, balanced, batched, and observable without leaking prompt content.

The Agent exposes that accelerator evidence through the same headless surface as the rest of the system. The `classifier` command derives the metrics endpoint from the configured classifier URL, applies the classifier timeout budget, normalizes the sidecar JSON, and returns either a structured warning for built-in or command-only modes or a renderable report for sidecar deployments. This keeps the Controller boundary observable without giving the metrics path permission to store prompt text or mutate routing configuration.

Routing uses hard context filtering before scoring. A model that cannot fit the estimated input and output window is removed before Softmax is applied, which prevents a visually confident but impossible route from reaching the Agent. The output side of that window can come from CLI `--output-tokens`, chat `max_tokens`, chat `max_completion_tokens`, Responses `max_output_tokens`, calibration samples, or the default estimate, which keeps context filtering and cost modeling tied to the request the developer is actually making. A request can also carry a maximum estimated cost or maximum estimated latency through metadata or the proxy headers `x-proofroute-max-cost-usd` and `x-proofroute-max-latency-ms`, allowing the Controller to reject over-budget or over-latency candidates before Softmax so hard operational ceilings cannot be overridden by quality preference. The policy can also arrive through `x-proofroute-policy` or through virtual model names such as `proofroute/local` and `proofroute/fast`, which keeps transparent proxy control available to clients that cannot easily mutate JSON request bodies or custom headers. Those aliases are listed from `/v1/models`, but they are stripped before provider execution so an upstream server only sees the concrete model selected by the router, while the Controller decision keeps the resolved policy as first-class evidence for response headers, telemetry, and terminal receipts. The model discovery response is intentionally self-describing: virtual aliases include their resolved policy, human-readable routing intent, and supported header or metadata controls, while executable models include provider, locality, context window, price, median latency, throughput, and best-fit intent metadata. This lets editor model pickers and SDKs explain the router before the first prompt is sent, reducing model-choice anxiety without adding a dashboard. Rejected models are still retained as structured evidence with the reason, required token budget, context window, executability, provider, locality, estimated cost, cost ceiling, estimated latency, and latency ceiling, so the trace can explain both why the winner won and why some models were never eligible. If every candidate is rejected, the Controller raises a structured no-route error with the same rejected evidence and the proxy returns an explicit 422 response instead of presenting a budget or context miss as an internal failure. The remaining models are scored with a blend of intent quality, context fit, local bias, requested-model bias, cost penalty, and latency penalty. Each candidate keeps those weighted components so a route can be rendered as an explainable trace rather than a black-box answer, and the probability distribution uses max-subtracted Softmax so very large positive or negative logits remain finite, which matters once real telemetry and dynamically learned weights enter the system. The Controller also keeps an in-process LRU route cache keyed by a short prompt hash plus token, output budget, cost ceiling, latency ceiling, policy, requested-model, and executability inputs; this avoids repeated classifier work without storing prompt text on disk, and proxy responses expose cache hits as routing evidence.

Dynamic policy weights sit above the scoring function rather than beside it. Balanced, save, fast, quality, and local policies all adjust the same quality, cost, latency, and local terms before Softmax is calculated. This keeps behavior tunable without introducing a second decision system, which is important for trust because every terminal explanation still comes from the same ranked candidate set.

The Agent is asynchronous by default. Proxy execution awaits exactly one selected provider path, while demo, proof, smoke, benchmark, calibration, and plan modes expose the router's value before any network call is made. Model discovery, readiness, CORS preflight handling, malformed JSON rejection, and proxy server lifecycle are also Agent responsibilities because they describe what the runtime can actually execute, not merely what appears in configuration. Local Ollama streaming is converted from newline-delimited JSON into OpenAI-style server-sent events, Anthropic streaming is converted from provider events into OpenAI chat completion chunks, OpenAI-compatible local and cloud streaming is passed through without buffering for chat completions, legacy Completions requests are adapted into the routed chat execution path and returned as text completion objects or chunks, and simple Responses API requests are adapted through the same route before being returned as Responses-shaped JSON or server-sent events. The runtime chooses protocol from provider kind rather than from the model's local flag, so a local OpenAI-compatible gateway can run without an API key while still benefiting from local routing bias, zero-price economics, and normal OpenAI-shaped request forwarding. When the selected provider returns a retryable 429 or 5xx failure, the Agent can retry the ranked fallback model and expose the switch through headers and telemetry, which keeps transient provider failure from turning an already-ranked route into a dead end. When a non-streaming upstream returns usage metadata, the Agent exposes actual token count, actual routed cost, and actual savings in response headers as well as the local ledger, giving SDK callers immediate evidence without asking them to parse a dashboard. Streaming routes cannot receive end-of-body usage headers after bytes begin flowing, so the proxy marks every response with stream state, usage proof source, and estimated token plan headers; non-streaming metered responses say `actual`, while streaming and unmetered responses say `estimate`. The proxy also lists the router proof headers in CORS exposure, sets `Timing-Allow-Origin`, and signs standard `Server-Timing` entries for router decision time and total proxy time, so browser-based editors and web sandboxes can read requested model, final model, model swap state, policy, intent, runner-up model, context window, context use, estimated route cost, baseline cost, savings percentage, speedup, selected latency, baseline latency, decision latency, router overhead percentage, cache state, stream state, usage proof source, classifier backend, classifier circuit state, classifier failure count, fallback state, token count, actual cost, actual savings evidence, and DevTools timing evidence after preflight instead of losing that proof behind default browser filtering. Those classifier guard, model-swap, context-use, cost-baseline, router-overhead, usage-source, and timing headers are deliberately prompt-free and protected from upstream overwrite, which makes them safe for browser display while still proving whether the request used the built-in classifier, an external accelerator, a protected fallback circuit, an estimate-backed streaming path, or a transparent model replacement whose routing overhead stayed small relative to the selected model's expected execution time. The launch demo routes a fixed suite of representative prompts and aggregates savings, speedup, labeled intent accuracy, route mix, policy mix, p95 router overhead, and p95 decision latency into a proof report, while the proof gate evaluates that report against explicit latency, overhead, savings, speed, request volume, accuracy, and optional classifier-circuit thresholds so the public performance claim can fail fast in CI instead of living only in README copy. The launch readiness path composes that proof report with repository metadata, proxy smoke, proxy matrix smoke, prompt-free privacy audit, SVG asset presence, and classifier evidence verification, keeping the maintainer release decision in the Agent layer where every claim can still be produced, skipped, warned, or failed as structured local evidence. Release packaging consumes classifier verifier output before it copies any original evidence file, copies raw classifier evidence only after a pass, and records failed verification without preserving a prompt-tainted or otherwise invalid submitted bundle in the public archive. The same proof gate can read the local telemetry ledger and evaluate real proxy traffic without prompt text, including a strict `--max-router-overhead-pct 1` guard for near-zero routing overhead and a strict `--max-classifier-circuit-open 0` guard that fails an accelerator deployment when repeated classifier timeouts forced protected fallback during the measured window. The smoke path starts a local fake OpenAI-compatible provider, routes a prompt, forwards an authenticated chat completion through the Agent runtime, and can also start the transparent proxy itself before calling `/v1/chat/completions`, which proves the SDK-facing entrypoint, CORS-exposed routing headers, upstream model swap, runner-up proof, context proof, cost proof, speed proof, router overhead header, Server-Timing proof, usage-source proof, and response parsing without cloud credentials. The proxy matrix smoke path keeps the same local proxy origin and the same endpoint while sending intent, context-window, and cost-ceiling cases through a synthetic model catalog, proving that the proxy changes final models for the right routing axis and that the resulting headers plus ledger remain prompt-free. The multi-agent planner produces a local fanout plan for architect, builder, reviewer, and optional specialist roles, while the fanout executor batches every executable-only route decision in one Controller pass and then dispatches the role prompts concurrently through configured providers before rendering status, latency, token usage, cost, savings, and output previews. These dry-run and execution modes are deliberately useful because they show whether an expensive model is being reserved for the part of the task that actually deserves it, then prove the distribution path can run when providers are configured.

Provider calls are bounded by an upstream timeout before the body is handed back to the proxy path. The global `router.upstreamTimeoutMs` value protects every provider by default, and an individual provider can override it with `timeoutMs` when a local daemon, remote gateway, or premium API has a different reliability envelope. A timeout is normalized into the same retryable failure channel as saturated or unavailable upstreams, so the Agent can execute the ranked fallback model instead of letting the transparent proxy stall inside a hung network hop.

The View treats the terminal as the product surface. It does not ask the user to trust a hidden score, and it does not bury the win in JSON unless JSON is requested. The default output is dense, colorful, and capture-friendly: the launch proof card, the launch readiness card, the shareable routing receipt, the CI-oriented proof gate, the drop-in proxy connection card with the browser-readable smoke proof command, shell-native proxy environment exports, the model catalog map, the classifier accelerator receipt, the proxy smoke receipt, selected model, requested-to-routed model swap state, resolved policy, detected intent, classifier backend, classifier guard state, ranked alternatives, weighted trace terms, savings, speedup, controller p95 latency, router overhead, calibration accuracy, prompt-suite economics, local routing ledger stats, telemetry-backed proof gates, and fanout economics are all visible in a single frame. The launch readiness card is deliberately framed for maintainers rather than end users: it shows whether repository metadata, zero-network value proof, proxy compatibility, privacy boundary, social assets, and classifier evidence are coherent enough to ship, with warnings preserved instead of hidden so a missing hardware evidence file cannot accidentally masquerade as a CUDA claim. The stats view can also run as a live watch surface, refreshing the current ledger window in place so a developer can keep savings, requested-model mix, model swap share, router overhead, policy mix, classifier mix, model mix, and latest prompt-free routes visible beside an editor while the transparent proxy handles real traffic. The share view has Markdown and SVG modes that preserve the same p95 latency, p95 router overhead, savings, speed lift, local-cloud split, intent mix, policy mix, classifier mix, model mix, model swap count, and copy line while stripping ANSI control codes, which lets the proof move from a terminal screenshot into GitHub, README hero assets, PR comments, and launch posts without translation. The classifier view now follows that same rule: sidecar metrics and classifier benchmarks can render SVG proof cards with device profiles, warmup state, p95 classifier latency, throughput, accuracy, batch mix, backend mix, and device mix, so the local accelerator story has a native social artifact instead of only a scrollback transcript. This is the growth loop of the project, because the fastest way to explain a routing engine is to show representative prompts becoming cheaper and faster routes in under a millisecond, then give the developer a line or generated visual they can paste into a launch post without translating the benchmark by hand.

The classifier benchmark proof extends that View contract to the local accelerator layer. It pushes a labeled prompt suite through the active builtin, command, or HTTP sidecar classifier, measures p95 classification latency and prompts per second, then renders backend, batch, lane, and device mix without emitting prompt text. When `--warmup` is combined with `--bench`, a sidecar deployment has to pass its `/warmup` proof before the benchmark report is accepted, which makes warmed weights, throughput, and accuracy part of one terminal receipt instead of separate rituals. Optional gates for p95 latency, labeled accuracy, throughput, minimum visible devices, minimum lanes, required device profiles, and required hardware probe profiles make the same proof usable in CI, while `--svg --out docs/proofroute-classifier-benchmark.svg` makes the same prompt-free proof portable into README updates, release notes, pull requests, and launch posts. The hardware probe gate is intentionally stricter than device profile presence: `--require-hardware-probe` only passes when the benchmarked profile set carries `source: nvidia-smi`, so a serious CUDA or TensorRT claim can distinguish bounded startup hardware discovery from manually declared marketing metadata. When `--evidence` is added to a JSON benchmark, the same report gains a prompt-free evidence bundle with sanitized command metadata, Node runtime, classifier mode, gate outcomes, device profiles, nvidia-smi profile counts, selected accelerator configuration, and SHA-256 hashes of local model, ONNX, or TensorRT engine files, which makes real hardware claims reviewable without leaking prompts. The verifier path `classifier --verify-evidence` recomputes those hashes, rejects tampered artifacts, requires recorded gates to pass, independently checks the recorded hardware probe gate when present, and turns missing device profiles or missing artifact hashes into a terminal failure, so a release claim can be checked later on the same machine instead of being trusted as a screenshot. The linear, ONNX, and TensorRT accelerator modules all sit behind the same NDJSON worker and HTTP sidecar contract: they load artifacts or engines during warmup, classify prompt batches without emitting prompt text, return logits as ranked intents through stable Softmax, and let the worker attach device, shard, batch, backend, and decision-latency metadata that the Controller and View can verify. This keeps multi-GPU classifier work honest: the sidecar can be powerful, but it has to prove in the same terminal frame or generated visual that it is fast enough, batched enough, and backed by enough named hardware to protect the zero-latency routing promise.

Configuration stays plain JSON to keep the system auditable. Providers describe execution endpoints and credentials, while models describe context window, price, latency, throughput, and per-intent quality. The defaults are useful as a demonstration catalog, not as universal truth. Production users should replace the model economics with observed telemetry from their own prompts, then tune the router weights so the terminal proof reflects the workloads they actually ship. The `init` command can emit either the default catalog or a local OpenAI-compatible preset, which keeps the first configuration step inside the same headless workflow instead of sending a developer to copy a recipe by hand. For developers already running LM Studio, vLLM, or a private OpenAI-compatible gateway, `PROOFROUTE_LOCAL_OPENAI_BASE_URL` appends an executable local zero-price model to the merged catalog after JSON configuration is loaded, which preserves the default demo surface while turning a local gateway into a routable candidate with no config file.

External classifier protection is part of the Controller boundary rather than an operational afterthought. The HTTP and command classifier adapters both keep a small failure counter and open a local fallback circuit after the configured failure threshold, then skip the external classifier during the cooldown window and return the built-in classifier immediately with circuit metadata attached to the intent features. This preserves the zero-latency routing promise under the exact failure mode that would otherwise hurt a transparent proxy most: a local accelerator that is installed, configured, and repeatedly timing out. The timeout still protects the first failure, the circuit protects the next requests, and a later successful classifier call closes the circuit so a recovered sidecar can rejoin the fast path without restarting the proxy.

The examples are intentionally executable rather than decorative. `examples/local-openai-router.json` demonstrates a local OpenAI-compatible gateway with no API key requirement, local pricing, local routing bias, and a command-backed classifier timeout, while `examples/classifier-command.js` proves the stdin/stdout classifier protocol for both `prompt` and `prompts`. The `examples/accelerator-worker.js` template keeps a hot NDJSON process alive, emits backend, device, batch, and decision-time metadata, can warm each visible accelerator device at startup, and can delegate classification to a user module through `PROOFROUTE_ACCELERATOR_MODULE`, which gives ONNX, TensorRT, vLLM, or private embedding code a narrow place to plug in without changing the sidecar or proxy contracts. The `examples/accelerator-module.js` adapter shows that delegated module shape in the smallest possible form: warm once per device, classify many prompts, and return prompt-free accelerator metadata that can flow through the sidecar metrics and proof views. The `examples/linear-accelerator-module.js` adapter goes one step further by loading a local intent model artifact, compiling weights during warmup, scoring each prompt shard with the same stable Softmax discipline as the Controller, and returning artifact-level evidence without storing prompt text. The optional `examples/onnx-accelerator-module.js` adapter preserves the zero-dependency default while showing how an installed ONNX Runtime package can turn the same feature tensor and logits contract into a native execution-provider-backed classifier. The `proofroute learn` command and the thin `examples/train-linear-intent-model.js` wrapper both use the Agent-layer intent training module, letting raw labeled samples or a `calibrate --json --out calibration.json` report update that linear artifact with an online calibration pass and write accuracy metadata into the generated model, while `examples/export-linear-intent-onnx.js` closes the artifact loop by generating `examples/linear-intent-model.onnx` from the plain JSON model as a minimal logits graph. The ONNX sidecar path therefore has a reproducible local model, a training story, and a direct bridge from ProofRoute's own calibration output before a team swaps in a heavier CUDA, TensorRT, or private classifier artifact. That gives the repository a copy-pasteable bridge from the zero-dependency demo to real local model servers and eventual GPU-backed classifier processes.

The same bridge is available through the public classifier CLI, because `proofroute-classifier` can spawn the accelerator worker as a persistent command, forward the accelerator module and model artifact through explicit CLI flags, and expose the artifact-backed path as a normal HTTP sidecar with warmup and readiness gating. The `examples/linear-accelerator-sidecar.sh` wrapper reduces that launch surface to one copyable command while keeping the entrypoint stable for operators and letting the underlying classifier evolve from deterministic rules to local model artifacts and eventually to heavier native runtimes.

Telemetry is local and deliberately narrow. The proxy writes a JSONL routing ledger that records requested model, final model, model swap state, provider, resolved policy, intent, classifier backend, classifier circuit state, token estimates, context window, context use, runner-up model, baseline model, candidate count, rejected count, rejected reasons, cost estimates, baseline cost, speedup, selected latency, baseline latency, status, decision latency, router overhead percentage, and timing while omitting prompt text and completion text. When a non-streaming provider returns usage metadata, the ledger keeps actual input tokens, output tokens, total tokens, actual routed cost, actual baseline cost, and actual savings; when usage is unavailable, the same ledger preserves the route estimate so streaming and failure paths still contribute to the proof loop. This creates the proof loop needed for an open source routing engine: the user can run the proxy during real work, call `stats`, and immediately see whether the router is saving money, replacing model-menu choices with better routes, applying the intended policy mix, keeping decision latency and router overhead low, and protecting itself from repeated classifier timeouts without exporting private development context. The stats path reads the ledger with diagnostics rather than brittle all-or-nothing parsing, which means a malformed JSONL record is skipped with a line-number warning while valid route evidence remains visible during a live coding session. The `privacy` command audits that same ledger by walking every JSONL object, counting evidence keys, failing on prompt-bearing, completion-bearing, request, response, authorization, secret, API key, raw text, or malformed records, and reporting only line numbers plus key paths so the proof command itself never prints the sensitive values it is designed to catch. The repair path is intentionally artifact-producing rather than in-place mutation: `proofroute repair --file .proofroute/events.jsonl --out .proofroute/events.repaired.jsonl` rebuilds a new JSONL file from allowed routing evidence, refuses to overwrite the source ledger, drops malformed records and records without trusted route evidence, and verifies that the repaired output remains prompt-free before downstream commands consume it. That repaired artifact can be audited with `privacy` and reused by ledger-backed `prove`, `share`, and `tune` through `--file`, while the original ledger remains available for inspection instead of being silently rewritten. Session windows such as `--since 1h` let `stats`, `share --ledger`, `prove --ledger`, and `tune` read the same recent slice of the ledger, so a screenshot, Markdown receipt, CI gate, and tuning recommendation can all describe the current coding session instead of an unbounded history. The same ledger can feed `privacy --file .proofroute/events.jsonl` before it feeds `share --ledger --markdown`, which turns a real coding session into a pasteable receipt while keeping the privacy boundary intact.

Tuning closes that proof loop without pretending to know more than the ledger can support. The tuner reads aggregated telemetry, estimates confidence from event volume, and recommends a policy plus router patch when the observed workload indicates stronger cost pressure, latency pressure, or local preference. It also watches classifier circuit counts and can recommend a classifier patch that shortens timeout and lengthens cooldown after protected fallback appears, which turns accelerator trouble from a passive warning into an explicit configuration review. It does not mutate configuration automatically, because the project should earn trust by explaining its recommendation before changing the routing surface. When the user explicitly asks for an export, the tuner writes a merged JSON configuration that can be reviewed, committed, shared, or discarded like any other local artifact.

Doctor diagnostics are part of the same headless experience. The command inspects the local Node runtime, configured model catalog, executable providers, lightweight upstream health, telemetry path, classifier mode, HTTP classifier sidecar health, and routing policy before the user points an editor, agent, or SDK at the proxy. Provider probes use local Ollama discovery or OpenAI-compatible model discovery when those endpoints are available, and an unreachable upstream is reported as a warning rather than a hidden surprise because the router can still classify locally and explain the missing execution surface. A configured classifier sidecar is probed through its derived `/health` endpoint so the terminal can show backend, lanes, warmed state, device profiles, and response time when the accelerator path is ready; an unavailable sidecar is also reported as a warning rather than a fatal error because deterministic local fallback preserves the routing path. When `--require-warmup` is used, the same health check becomes a deployment gate and fails a cold sidecar, which gives teams a simple CI or startup guard for multi-GPU classifier workers that must be warmed before proxy traffic starts. The proxy process can apply the same rule with `--require-classifier-warmup`, checking the sidecar's `/ready` endpoint before listening so a cold accelerator cannot receive the first real coding request by accident. This keeps the first run honest: a passing doctor output means the transparent proxy has at least one route it can execute against a reachable provider, a warning means routing is alive but execution deserves attention, and a failing output names the missing local or cloud prerequisite without requiring a browser dashboard.
